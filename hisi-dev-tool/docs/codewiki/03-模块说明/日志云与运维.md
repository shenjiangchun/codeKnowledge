## 1. 模块概述

### 1.1 职责定义

**核心职责**：把一条异常日志（手动提交、从日志云定时拉取、或随请求采集上报）变成有证据支撑的根因分析报告：解析堆栈 → 到知识图谱取证 → 形成假设 → 确定性验证 → 成文，并支持追问、导出与相似报告聚合。

| 本模块负责 | 本模块不负责 | 由谁负责 |
|-----------|-------------|---------|
| 堆栈解析、指纹去重、图谱取证、假设与验证、报告成文 | 图谱的构建与检索实现 | [知识图谱构建](./知识图谱构建.md)、[Neo4j图存储与检索](./Neo4j图存储与检索.md) |
| 日志云 HTTP API 查询、定时拉取配置 | 日志云本身 | 外部日志云服务 |
| 报告的落库、列表、导出、追问 | APM trace 诊断 | [APM故障诊断](./APM故障诊断.md) |
| 健康检查等运维接口 | 应用配置读写 | [会话与工作区](./会话与工作区.md)、[远程项目管理](./远程项目管理.md) |
| 把报告聚合成待办 | 修复执行 | [工作台与自动修复](./工作台与自动修复.md) |

### 1.2 LLM 调用边界

本模块的模型调用全部经 `AgentLlmClient` / `ReActSession`，**属 agent 类流程，经 pi**：

| 调用 | 入口 |
|------|------|
| v1 分析节点 `ClaudeAnalyzeNode`（三轮递进） | `AgentLlmClient`（清单 `one-shot`） |
| v2 假设、综合、可选评审 | `AgentLlmClient`（清单 `one-shot`） |
| 日志追问 | `ReActSession`，取声明 `log-followup`（清单 `log-analysis`，skill `log-triage`） |

源码里仍有 `Claude` 字样的类名与注释（如 `ClaudeAnalyzeNode`、`loganalysis/nodes/` 下的 Javadoc）不代表底层是某个厂商的 SDK。

## 4. 分析流程

### 4.1 v2（当前主路径）

`LogAnalysisV2Orchestrator`：`ParseNode`（复用 v1）→ `LogKgEvidenceNodeV2` → `LogHypothesisNodeV2` → `LogVerifyNodeV2` → `LogSynthesisNodeV2` → `ReportNode`（复用 v1）。节点间以 `Map` 传递上下文。

```mermaid
sequenceDiagram
    participant C as 客户端
    participant EX as LogAnalysisExecutorV2
    participant OR as LogAnalysisV2Orchestrator
    participant KE as 图谱取证
    participant HY as 假设
    participant VF as 验证
    participant SY as 综合
    participant DB as log_analysis_report
    participant WS as /ws/log-analysis

    C->>EX: POST /api/v2/log/analyze
    EX->>DB: 建报告行（pending）
    EX-->>C: reportId
    Note over EX: analysisTaskExecutor 异步
    EX->>OR: run(initialInput, reportId)
    OR->>KE: 精确优先取证，产出证据包
    KE-->>OR: evidencePackV2 / evidenceAnchors / codeBodiesV2
    OR->>HY: 生成假设（每条须引用证据编号）
    HY-->>OR: hypothesesV2
    OR->>VF: 引用完整性、根因落点、因果链连通性
    VF-->>OR: verificationV2
    OR->>SY: 把通过的假设写成报告
    SY-->>OR: markdown
    OR->>WS: NODE_START / NODE_COMPLETE / NODE_ERROR / DAG_COMPLETE
    EX->>DB: 更新为 completed
    C->>WS: 订阅 ?reportId=
```

| 节点 | 要点（据类注释） |
|------|------|
| `LogKgEvidenceNodeV2` | 堆栈帧本身就是精确坐标：先按「类名.方法名」精确命中，未命中才回退语义检索并标记为模糊证据；按堆栈先后确定「抛出点」与「调用方」；除下游调用树外还取上游调用链；取抛出点直接下游方法的源码；图谱里没有源码的方法按堆栈文件名与行号从本地源码读取（`SourceSnippetReader`） |
| `LogHypothesisNodeV2` | 一次 LLM 调用给出按置信度排序的根因假设，最多 3 条，每条必须引用证据编号；模式类型改由异常名的确定性规则判定；LLM 不可用时 `hypothesesV2` 为 null |
| `LogVerifyNodeV2` | **不调用模型**的确定性检查：引用是否都在证据包里、指认的根因方法是否精确存在于图谱、根因是否位于某个堆栈帧的上游调用链上。因果链状态取值 `verified`、`stack_verified`、`unverified`、`unknown`、`at_throw_site`。可选评审：`loganalysis.v2.evaluator.enabled=true` 时由一次独立的 LLM 调用充当评审 |
| `LogSynthesisNodeV2` | 输入只有「通过验证的假设 + 证据」；成文后再做一次引用校验，编造的引用替换为「未验证」并拉低置信度；LLM 不可用时由证据直接生成确定性报告 |

证据机制（`agentflow` 包）：`EvidencePack` 按加入顺序编号 `E1`、`E2`…；`EvidenceAnchor` 的 `kind` 取值 `frame` / `method` / `semantic` / `source` / `upstream` / `entry` / `downstream` / `sql` / `bridge`；模型用 `[[E n]]` 引用；`GroundingVerifier` 做集合运算判定是否有编造引用；`Citations` 负责提取、标记与转写。

`LogAnalysisExecutorV2` 与 v1 写同一张 `log_analysis_report` 表、同一组列，所以 v1 的读接口对 v2 报告同样有效；v2 只在 `root_cause` 里多存 `evidenceAnchors` 与 `verification`。v2 没有产出报告时回退到 v1。

### 4.2 v1

`LogAnalysisDagOrchestrator`：`ParseNode` → `KgSearchNode` → `CodeContextNode` → `ClaudeAnalyzeNode` → `ReportNode`。无检查点缓存（日志是一次性分析）、无 HITL 暂停。

| 节点 | 要点 |
|------|------|
| `ParseNode` | 从原始日志抽取异常类型、根因异常、非框架的关键栈帧、供图谱检索的方法签名；识别 `HISI_CAPTURE` 信封并解码 |
| `KgSearchNode` | 经 `KgMcpClient` 按栈帧检索图谱；递进搜索：第一批结果为空时继续搜后续帧（每批 5 个，最多 3 批） |
| `CodeContextNode` | 从图谱加载方法体作为代码上下文 |
| `ClaudeAnalyzeNode` | 三轮递进：模式识别（2000 token）→ 因果推理（8000 token，输出 Markdown）→ 修复方案（4000 token）；前一轮失败时按注释所述逐级降级 |
| `ReportNode` | 整理成结构化报告，准备落库 |

### 4.3 报告状态与去重

| 项目 | 说明 |
|------|------|
| 报告状态 | `pending` → `processing` → `completed` / `failed` |
| 指纹 | `FingerprintService`：错误类型 + 前 3 个非框架栈帧（类名 + 方法名，不含行号） |
| 出现次数 | `occurrence_count`（默认 1）：同一指纹重复出现时累计 |
| 向量相似 | `log_error_embedding_map` 记录报告与向量嵌入的对应及相似度，阈值列默认 0.85 |

`AnalysisPipelineService`（四节点流水线：解析 → 去重 → 分析 → 完成）、`RootCauseAnalysisService(Impl)`、`CaseMatchingService(Impl)`、`AIAnalysisPromptService` 在主代码中没有调用方；`CaseMatchingServiceImpl` 仍以 `@PostConstruct` 建 `diagnosis_cases` 表。

## 10. 错误处理

| 场景 | 处理 |
|------|------|
| v2 未产出报告 | 回退到 v1 流程 |
| v2 假设阶段 LLM 不可用或输出不合法 | `hypothesesV2` 为 null，后续节点走确定性降级 |
| v2 综合阶段 LLM 不可用 | 由证据直接生成确定性报告 |
| 编造的证据引用 | 替换为「未验证」并拉低置信度 |
| v1 前一轮失败 | 逐级降级（单轮回退 / 用前一轮假设当根因并给默认建议） |
| 分析失败 | 报告 `failed` |
| 拉取某应用失败 | 记日志，继续其他应用 |
| 重复日志 | 按指纹跳过分析 |
