## 资产层 — 工程产物

### A. OTel 必开开关清单

```bash
-Dotel.exporter.otlp.protocol=http/protobuf
-Dotel.instrumentation.opentelemetry-api.enabled=true
-Dotel.span.attribute.value.length.limit=8192
-Dotel.instrumentation.logback-mdc.enabled=true
-Dotel.instrumentation.log4j-mdc.enabled=true
-Dotel.instrumentation.jdbc.enabled=true
-Dotel.instrumentation.spring-webmvc.enabled=true
-Dotel.traces.sampler=parentbased_always_on
```

日志 pattern 强制 `%X{trace_id} %X{span_id}`。

### B. Prompt 骨架 + 护栏

```text
# 角色
你是资深 Java 故障定位专家，严格基于证据推理，不臆测。

# 异常证据
{exception_class} @ {throw_location}
Message: {exception_message}
Stack(top 8): {stack_top_frames}

# 调用链上下文（KG 2 跳）
入口: {root_entry}
路径: {call_path_compact}
关键方法签名: {key_method_sigs}

# 运行时数据
入参: {input_params_json}
关键变量快照: {var_snapshots}
{branch_specific_section}

# 任务
1. 根因(1句，定位到行)
2. 证据链(引用上述编号)
3. 修复建议(代码片段，≤20行)
4. 置信度(高/中/低)+理由

# 护栏（不可违反）
若上述 evidence 中无 status=ERROR 且无耗时显著偏离基线的 span，
必须返回 {"rootCause": null, "confidence": "LOW", "reason": "INSUFFICIENT_EVIDENCE"}，
严禁基于方法名/类名猜测根因。

输出 JSON: {root_cause, evidence, fix, confidence}
```

### C. Token 丢弃优先级（先→后）

1. `userRequest.body` 截到 512 字符
2. KG 2 跳叶子节点
3. `affecting` 上游链
4. silentCatchBlock 降为一行
5. exceptionBlock stack 折叠 top-5 帧
6. **永不丢**：分支指令 + JSON Schema + 异常类型 + throwSite

### D. FailureLocatorPromptBuilder 接口

```java
public class FailureLocatorPromptBuilder {
    private static final int MAX_TOKENS = 4500;
    public String build(BuildContext ctx);
    ExceptionEvidence pullExceptionEvidence(String traceId);
    List<SilentCatchSpan> pullSilentCatch(String traceId);
    CallGraph fetchCallGraph(String className, String method, String projectPath, int depth);
    ExceptionType classify(ExceptionEvidence ev);
    String renderBranch(ExceptionType type, PromptParts parts);
    String trimToBudget(PromptParts parts, int budget);
}
public record BuildContext(String traceId, String spanId, String projectPath, UserRequest userRequest) {}
```

### E. 3 个验收用例

| 用例 | 场景 | 验证点 |
|------|------|--------|
| A | `throw new RuntimeException` baseline | exception event 非空 + stacktrace 完整 |
| B | `catch{ return null }` silent catch | `suspicious.silent_catch=true` + 无 exception event |
| C | 异步线程异常仅 warn 日志 | 父子 span 同 trace_id + 日志 trace_id 一致 |

## KPI 与撤回开关

### 第一周 KPI

| KPI | 阈值 | 不达标砍什么 |
|-----|------|------------|
| 一次跑通率 | <60% | 砍 AI 复杂度，回退纯模板 |
| D3 用户回访率 | <20% | 加历史 trace 一键复跑 |
| AI 建议采纳率 | <15% | 砍 AI 输出，强化降级层 |

### 撤回开关

- 保留：错误码字典 + 人话错误页
- 隐藏：移除 AI 主入口，降为二级菜单
- 对外：「错误码百科已稳定运行，AI 分析功能转入内测打磨」

## 完整 5 轮讨论过程

### 第一轮：各抒己见
- **务实派**：砍模板和多策略，3 天 MVP 跑通固定证据包+一个 prompt
- **APM 专家**：trace 为骨日志为肉，extension finally 段强制 recordException，无 traceId 日志丢弃
- **Prompt 工程师**：富 prompt 必须分层重组，异常 span 置顶，KG 裁剪 2 跳
- **魔鬼代言人**：假设式设计，60% 项目不打异常日志，debug 期看 IDE 更快，只做手动按钮

### 第二轮：交叉质疑
- 务实派接受 recordException 兜底 + traceId 强关联
- APM 专家妥协 MVP 用 OTel 原生不自研字节码
- Prompt 工程师接受"1 骨架+章节分支"
- 魔鬼代言人指出 4 大坑（类加载/MDC/KG/LLM 配额）+ catch 吞异常 OTel 救不了

### 第三轮：收敛边界
- 4 大坑应对策略（降级/绕过/砍场景）敲定
- OTel 必开开关清单出炉
- silent_catch 启发式定型
- Prompt 骨架定型 + Token 4500 + KG 2 跳 + 不带 few-shot

### 第四轮：价值排序
- 11 条 5 天任务清单
- 3 个验收用例代码
- FailureLocatorPromptBuilder 接口
- 3 个第一周 KPI + 4 类人话错误页

### 第五轮：终辨
- silent_catch 缓做仅留强信号（务实派）
- silent_catch 误报陷阱护栏（APM 专家）
- 证据不足必须返回 LOW confidence 护栏（Prompt 工程师）
- 撤回开关：保留错误码字典（魔鬼代言人）
