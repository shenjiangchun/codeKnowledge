## 4. 内部实现

### 4.1 字段白名单

`query()` 与 `analyze()` 都先建一个空对象，再逐个判断「入参里该字段 `!== undefined`」才放进请求体。效果：

- 入参里出现 schema 之外的字段（包括入口自动注入的 `projectPaths`、`projectPath`）不会发给后端。
- 未传的可选字段不会以 `null` 或 `undefined` 的形式出现在请求体里。

### 4.2 路径参数

`report()` 与 `reportStatus()` 把 `reportId` 直接拼进 URL，没有做 URL 编码，也没有从 `number` 转字符串。

### 4.3 处理函数

实例由模块级变量 `_logTools` 惰性创建，进程内只创建一次；入参经类型断言后直接传给对应方法。

## 8. 错误处理

| 错误场景 | 处理 | 调用方感知 |
|---------|------|-----------|
| 后端返回非 2xx（例如入参超长） | `ApiClient` 抛 `HTTP <code>: <body>` | `{ success: false, error, tool }` + `isError` |
| 后端业务失败（HTTP 200，`code` 非 200） | 本模块不判断，原样透传 | 调用方需检查 `code` 与 `message` |
| 报告未完成就取详情 | 后端在 `code` 里返回 400 并带当前状态 | 调用方应先轮询 `log_report_status` |

## 10. 已知问题与扩展点

| 已知问题 | 影响 |
|---------|------|
| `log_query` 与 `log_analyze` 被登记为宽松工具：设了范围后入口会给入参追加 `projectPaths` / `projectPath`，但本模块的白名单不会把它们放进请求体 | 项目范围对这两个工具没有实际作用 |
| 后端 `LogAnalyzeRequest` 有 `projectPath` 字段（注释说明用于 KG 检索），但 `log_analyze` 的 schema 没有声明该字段，白名单也不转发 | 即使 AI 传了 `projectPath` 也不会到后端 |
| 后端 `LogQueryDto` 有 `sortBy` 字段（默认 `@timestamp`），工具没有暴露 | 只能按时间排序 |
| `log_analyze` 的 schema 不强制 `message` / `stackTrace` 至少一个 | 两个都缺时后端在 `code` 里返回 400 |
| 文件头注释把日志级别写成「ERROR/WARN/INFO」，schema 的枚举里还有 `DEBUG` | 只影响阅读 |

| 扩展点 | 扩展方式 |
|--------|---------|
| 暴露 `sortBy` | schema 加字段，并在 `query()` 的白名单里加一行 |
| 让 `log_analyze` 带 `projectPath` | schema 加字段，并在 `analyze()` 的白名单里加一行 |
