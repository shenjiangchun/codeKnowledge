# 圆桌讨论记录：APM 失败链路定位器技术实现

## 一句话结论

5 天 26h 后端 MVP（D1 基础 8h / D2 异步链路 10h / D3 集成砍线 8h），叠加 UI 圆桌 D4-5 9.8h。**异步 reportId + 纯轮询 + Caffeine 三缓存 + 统一错误码 + 5 特性开关**，落地"扛得住跑不通也能优雅降级"的失败链路定位器。

---

## 一、技术架构总览（R1-R3 收敛）

| 项 | 决定 |
|---|---|
| 通信模式 | 异步 reportId + 纯轮询（1.5s，超 20s 退避 3s） |
| OTel 接入 | 不用 advice 字节码改写，silent_catch 移到 SpanIngestionService（QA 否决） |
| 缓存 | Caffeine 三件套：exceptionSpanIndex(2h/10k) + diagnosisDedupCache(30min/2k) + diagnosisReportStore(2h access) |
| 线程池 | apmDiagnoseExecutor core=4 max=8 queue=64 CallerRunsPolicy |
| 锚点 | className#methodName @ filePath:startLine ±3 容差（MethodNode 无 endLine） |
| 流控 | Guava RateLimiter(2 QPS) + Semaphore(4) + LinkedBlockingQueue(50) 三闸 |
| Token 预算 | jtokkit cl100k_base 精确计数，trimToBudget 裁剪 |
| 错误码 | 统一枚举 1xxx OTel / 2xxx 接入 / 3xxx 诊断 / 4xxx LLM / 5xxx KG / 9xxx 测试 |
| 多 tab 隔离 | sessionStorage + apmStore.diagnoses Record 按 traceId 隔离 |

## 七、5 个特性开关（回滚预案）

```yaml
feature.apm.diagnose:
  enabled: true              # 整模块下线（菜单+路由+controller 401）
  silent-catch: true         # false 只采异常 span
  llm-stream: false          # MVP 默认关，走同步
  kg-enrich: true            # false 跳 KG 关联
  rate-limit-qps: 2          # 热调，0 即断流
```

## 十、四轮讨论概要

### R1 各抒己见
- 后端架构师：异步 reportId + Caffeine 缓存
- OTel 专家：ByteBuddy advice 4 大坑（加载序/MDC/异步丢 trace/字节码冲突）
- LLM 工程师：jtokkit 精确计数 + 三闸流控
- 前端工程师：sessionStorage + AbortController + onScopeDispose
- QA：fixture-generator 独立模块
- 魔鬼：质疑 SSE 必要性、agent 热插拔可行性

### R2 交叉质疑
- QA 否决 advice 内做 silent_catch（不可测）→ 移到 SpanIngestionService
- 后端让步：缓存 TTL 30min → 2h 覆盖午餐
- LLM 让步：去流式，MVP 同步 + 超时 60s
- 前端让步：Pinia 持久化用 sessionStorage 而非 localStorage

### R3 强收敛
- 通信定型：纯轮询 1.5s + 20s 退避 3s
- MethodNode 字段事实核查：无 endLine → 锚点降级 startLine + ±3
- 11 文件路径/LOC/职责完整出码
- 错误码段位划分敲定

### R4 优先级与验收
