# 首页工作台 · 设计原型（三版）

一次性原型，用来回答「首页工作台应该长什么样」。选定版本后，这里的代码和截图会被真正的实现替换。

## 怎么看

- 启动前端后，点侧边栏顶部的「工作台原型」，或直接打开
  `http://localhost:5173/prototype/workbench?variant=A`（`B`、`C` 同理）。
- 底部悬浮条或键盘 `←` `→` 切换版本；三个版本共用同一份内存状态，切过去进度还在。
- 数据是样例（见下），点「自动修复」会在内存里模拟后台流程；「重置演示」可以重来。
- 只在开发构建里出现，生产构建不渲染入口和切换条。

截图：`A1`–`A4` 分诊台，`B1`–`B2` 流程看板，`C1`–`C2` 清零指挥台。

## 三版各自回答的问题

三版用同一组数据、同一套 8 个阶段，区别在「为什么这样排布」。

### A 分诊台 —— 最快对一条待办做决定

三栏：左边筛选（状态 / 来源 / 项目 / 严重度），中间密集列表，右边是选中项的详情。
详情里按做决定的顺序排：为什么重要 → 证据（带图谱给出的因果链和置信度）→ 影响面（调用方、相关测试、可能触及的文件）→ 建议 → **自动修复**。

修复智能体住在底部可折叠的「坞」里：收起后是一行 38px 的状态条，每个运行中的修复一个标签，
百分比照常跳；展开是阶段步进条 + 当前阶段的产物 + 实时日志。停在「方案确认」时坞自动变高，把候选方案和确认按钮完整露出来。

- 强：单条待办的上下文最完整，决定成本最低；「随时打开关闭」最直接。
- 弱：看不出全局（还剩多少债、哪个项目最严重），也不支持批量。

### B 流程看板 —— 流程状态最大化可见

每一列是 SDD 的一个阶段，卡片自己往后走；空列收成细轨，所以 8 个阶段一屏放得下。
「方案确认」一列有底色，因为整个流程里只有这一步必须有人。点开卡片是右侧抽屉：纵向时间线，
每个阶段的产物挂在对应节点上（证据、候选方案、Spec、任务与 diff、测试结果、E2E 步骤、分支与提交）。

- 强：一眼看出每个修复卡在哪一步；「需要你」在版面上是天然的视觉焦点；迭代回路（E2E 失败回到开发）看得很清楚。
- 弱：待办一多，第一列会很长，不适合逐条分诊；没有全局数字，也不能批量。

### C 清零指挥台 —— 把「技术债清零」当成可度量的目标

顶部是目标本身：余额、清零进度、近 7 天清了多少、按这个速度还要多久，外加按项目的进度条。
中间是可勾选的表格（证据强度、近 7 日趋势、状态 / 进度都在行内），支持「批量自动修复」；
左边是「项目 × 来源」的热力筛选。底部常驻「修复流水线」，点开是全屏运行监视器：
左栏纵向时间线和运行元数据，中间是阶段产物，右栏实时控制台。

- 强：唯一能回答「离清零还有多远」的版本；表格对大量待办、多项目最扛得住；监视器最适合盯长时间运行的智能体。
- 弱：信息密度最高，单条待办的证据要点开才能看全；首屏比另外两版重。

## 三版共同的约定

- 待办 = 日志分析 issue + 架构诊断 issue，统一字段：严重度 P0/P1/P2、证据强度（置信度 + 因果链状态）、影响面、出现趋势。
- 状态：待处理 → 修复中 → 待你确认 → 已清零；另有「已忽略」。
- 自动修复的 8 个阶段：代码实证 → 方案确认 → Spec 生成 → 任务拆分 → 迭代开发 → 用例回归 → 本地 E2E → 提交推送。
  - 方案确认是唯一必须人参与的节点；其余阶段自动推进。
  - 回归或 E2E 失败会回到开发，形成迭代回路，界面上显示「第 N 轮」。
  - 提交推送 = 在独立 worktree 的分支上提交并推送，不自动合并主干。

## 样例数据

- 日志待办里的 reportId、异常类型、服务名取自库里现有的报告；只有少数几条是真实分析结果，其余是为了体现多项目而编的。
- 架构待办 I-01 ~ I-09 是 2026-11-24 晚那次架构深度分析的真实产出。
- 运行时长、任务、diff、测试数字都是演示值。

## 后端现状（决定实现要补什么）

已有的底座：DAG 执行器与 HITL 事件、SSE 事件流、现有修复引擎的 worktree / 提交 / 单类测试、进程启动、图谱取证节点。

还没有的：

- 跨项目聚合：日志报告列表不带项目字段，架构问题不带项目路径，也没有 issue 级的稳定 ID。
- Spec 生成与任务拆分：没有任何持久化的产物。
- 回归执行器与 E2E 执行器：现有引擎只跑一个测试类。
- 推送编排：后端任何地方都没有 `git push`；也没有确认 / 恢复修复会话的接口。
- 架构问题进入修复流程的入口：现有引擎只接受日志报告 ID。
